# 会话首次导入性能对照

## 2026-10-19：按内容分配搜索索引与完整启动准备

### 全量真实历史初始化

删除指定测试数据目录后，使用当前编译产物从本机各客户端的实际默认位置重新发现历史，不配置样本来源、不限制会话数量。发现 7,976 个来源，全部重新解析，快速复用、校验复用和确认缺失均为零。发布后按会话身份去重为 7,975 个会话，包含 1,878,436 条消息，覆盖 12 类客户端来源。

| 范围 | 旧目录保留的首次运行记录 | 本次从空目录运行 | 耗时变化 |
|---|---:|---:|---:|
| 历史导入、索引及完整版本发布 | 31 分 39.3 秒 | 14 分 9.7 秒 | 减少约 55.3% |
| 启动准备完成 | 33 分 39.6 秒 | 15 分 58.4 秒 | 减少约 52.5% |

旧记录来自该测试目录原有的任务和生命周期日志，包含 7,962 个来源；本次多 14 个来源，且新实现预热全部默认总览区域与周洞察，旧实现仅预热概况。旧总时长以服务就绪至数据就绪计，新总时长包含 CLI 启动开销。这是两次同机实际运行的对照，不是完全固定输入和工作量的严格基准；没有主动清空操作系统文件缓存。

本次选择 4 个解析线程。总览准备阶段约 1 分 39 秒；完成后再次 `web --no-open --json` 约 0.36 秒，默认总览七个区域与周洞察接口约 10～16 毫秒返回。每五秒采样的后台峰值 RSS 约 1,561 MiB，主库与 WAL 合计采样峰值约 9,134 MiB。

验收确认对话索引覆盖 125,118 条对话消息、字符索引覆盖全部 1,878,436 条消息，两者完成标记均有效。中文单字、双字与英文长词 API 查询、会话正文读取和真实浏览器的总览及会话搜索均通过，未发现控制台错误。默认首屏缓存完成后才返回启动地址；没有注册仓库，不创建地图任务。原始输入、任务标识、详细计时和查询响应仅保存在本机忽略目录。

### 固定样本对照

本轮使用相同的固定真实来源样本，在隔离数据目录对照当前修改前后的实现。74 个来源约 122 MiB，覆盖四类客户端；每组取三轮中位数，不主动清空操作系统文件缓存。计时覆盖导入至完整历史版本发布，不包含默认总览缓存和网页渲染。

| 方案 | 完整历史发布 | 峰值 RSS | 主库与 WAL 采样峰值 |
|---|---:|---:|---:|
| 修改前，2 个解析线程 | 19.72 秒 | 619 MiB | 128 MiB |
| 按内容分配索引，2 个解析线程 | 8.16 秒 | 733 MiB | 107 MiB |
| 按内容分配索引，4 个解析线程 | 6.96 秒 | 978 MiB | 109 MiB |

双线程样本耗时降低约 58.6%，四线程约 64.7%；四线程额外占用内存。这些是固定样本的测量，不外推为整份历史或其他机器的保证。每轮均保留 22,672 条消息、3,726 条用量、74 个修订，完整正文、元数据、用量、指纹及六组 API 搜索结果的摘要一致。

搜索按内容范围分配索引：用户与 AI 对话沿用精确 trigram 候选，工具、思考、上下文等全过程保留字符词项索引，过程长词由相邻双字候选与原文核验。样本中对话正文约 1.1 MiB、工具结果约 32.5 MiB，减少对大量过程内容重复进行原文 trigram 分词的工作。原始正文不截断、查询结果范围不缩减；大范围过程长词可能需要更多原文核验，建议带会话、客户端或项目范围。

解析线程先合并批次内同一身份的流式快照，再进行词项编码；写入批次按实际保留值估算，不把已替换快照累计成重复批次。旧全记录 trigram 在新对话及全过程字符索引完整后回收，补齐前保留有效的旧候选。

每轮按 CPU 和内存选择 1～4 个解析线程；少于八个来源直接解析。CPU 至多使用可用并行度的一半，整机每 2 GiB 内存允许一个线程；进程可用内存预留 512 MiB，再按每线程 256 MiB 限制。此预算用于保守选择，不是单条记录或整个应用的严格内存上限。运行中不根据短时负载反复伸缩，SQLite 保留单写入者。

首次 `start`、`web` 等待完整历史、用量及默认总览全部首屏缓存，终端展示实际阶段、数量和耗时。没有仓库时跳过地图，已有可查询历史的旧目录快速返回；空库先保存准备中标记，首次中断后仍等待完整准备。完成标记不要求与每次增量版本相同，结果缓存仍逐版本核验。准备失败或等待超时不打开浏览器，不停止后台。

同一固定样本使用编译后的 CLI 实测一次：空目录 `start` 约 9.47 秒，包含默认总览缓存；再次 `web --no-open --json` 约 0.26 秒，复用已就绪实例。随后默认总览七个区域及周洞察接口约 8～15 毫秒返回，浏览器确认总览、无仓库状态及会话搜索可用。该单次应用检查与上表三轮导入基准分别记录，不作为整份历史的预计耗时。

完整测试 1,664 项、CLI 测试 43 项通过；额外核对八个查询、四类消息范围的 96 组 API 结果一致。类型、翻译完整性、构建与公开内容检查通过。

详细来源、逐轮计时和浏览器检查留在本机忽略目录。下文保留早期测量作为历史记录，其默认并发及双索引实现已由本轮替代。

## 等价检查

12 轮均得到 74 个会话修订、22,672 条消息、3,726 条用量记录。按来源与稳定消息身份排序比较完整正文、消息元信息、用量、会话元数据、指纹及六组搜索结果，摘要完全相同。两类 FTS 的完成状态与文档数量均核对通过。

六组查询为中文单字、双字及英文样本，包括“锁”“的”“事务”“你好”“transaction”“commit”。摘要覆盖 API 返回的分组、命中和精确计数；不以相同总数代替结果内容检查。

JSONL 流读取次数由 247 次降为 183 次，记录的流读取字节由 381.36 MiB 降为 267.61 MiB，减少约 29.8%。这包含受监测来源流的重复检查与解析，不表示物理磁盘实际读取量，也不包含其他 SQLite、目录或旁路元信息 I/O。

## 采用的改动

1. 首次主解析读取同时计算字节哈希，保留结束时固定前缀校验。
2. 有界解析线程预计算字符词项，批次确认后继续；数据库保留单写入者与触发器。
3. 首次导入较大批次提交，辅助查询索引统一后建，首次发布仍等待完整就绪。
4. 保存已校验来源检查点，中断后核验复用；未完成来源清理，成功发布和来源缺失时回收。

批次按条数或估算字节触发提交，单条大消息可超过批次目标，仍沿用解析器单条来源记录上限。

## 结论边界

代表样本的默认路径耗时降低约 19.6%，同时增加约 244 MiB 峰值 RSS。四线程耗时降低约 23.1%，内存更高。该结果不直接外推为整份真实历史的重建时长，也不表示所有客户端、文件分布与机器均有相同比例的收益。已有完整索引的普通启动与全量重建分别看待。
