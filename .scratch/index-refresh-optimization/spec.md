# 索引增量、自动刷新与页面性能优化

Status: resolved

用户于 2026-10-09 明确授权开发，并要求优先保证数据正确性和性能。未逐项选择的首轮选项按推荐方案执行：后台分批回收、自动应用新版并保持阅读位置、网页可见时检查全部 Agent。

## 目标

1. 无变化来源复用，变化来源尽量按记录更新，减少重复解析、正文写入与派生统计计算。
2. 网页可见期间自动检查并在完整发布后显示新数据，保持用户阅读状态。
3. 降低首屏画像、轨迹、消息和地图载荷；查询只读取所需范围。
4. 自动归还已释放数据库空间，减少空闲页和伴随文件长期占用。

## 沿用的边界

- 原始来源只读，内容、搜索、轨迹、用量、资源证据和事件身份完整保留。
- 快速检查与完整校验保持区别；确认缺失才排除，临时失败保留有效结果。
- 来源变化判断按具体来源及依赖进行；Agent 最近检查时间不能替代来源级变化判断。
- 更新完成后原子发布完整版本；新旧版本可共享未变化内容，但不就地修改已发布内容。
- 当前客户端、来源格式和容器身份保持区别，不能按客户端名称假定追加能力。
- 原有手动刷新范围、语言偏好、资源管理状态和恢复材料保持既有生命周期。
- 不通过删减历史或关闭全文搜索达到性能目标。

## 增量流程与本次取舍

- 记录来源身份、变化指示、内容校验、旁路依赖和解析规则；地图沿用已有的安全续读状态。
- 未变来源复用；地图确认追加时处理新增记录与受影响的尾部状态；改写、截断、替换或依赖失效时回退到对应来源重处理。会话变化来源仍完整解析。
- 无可靠追加边界的原生容器保留快检与来源级复用，记录级更新能力单独核验。
- 地图只重写变化来源缓存，按历史和仓库基线依赖更新受影响结果。
- 评估内容块共享与版本成员关系，避免追加少量记录产生完整正文副本。
- 分片和有限并行属于性能候选方案。本次固定对照先验证了共享路径／Git 检查缓存和无变化复用的收益；解析保持原顺序，不在缺少收益与一致性证据时增加 CPU 分片。
- 会话变化来源保留完整解析，因为用量、最终回答和分支复制可能影响旧记录；记录级续读状态机另行设计。地图沿用已验证的追加边界及改写回退。

## 自动刷新

- 页面可见时默认每 60 秒检查，多个标签页合并服务端任务，运行中不重复排队。
- 全部页面隐藏后暂停新自动检查，已开始任务正常结束；返回可见时按最近检查时间补查。
- 没有来源或依赖变化时不重写正文，不制造无意义版本，也不重取大接口。
- 当前代码地图只自动检查当前仓库；历史刷新不无条件触发所有仓库地图重算。本次不新增当前会话优先队列。
- 新版自动应用并保留阅读位置；自动检查全部 Agent，不改变手动刷新范围。
- 复用现有摘要接口检测结果版本；自动检查触发索引更新，与读取已发布版本分别调度。
- 新版消息、画像和轨迹准备完成后一起切换；等待期间保留同一旧版画面，不将不同版本混合成当前结果。
- 优先按稳定消息身份定位阅读位置，轮次序号只作为回退；保留会话选择、筛选和地图视野，定位失效按现有消息定位反馈处理。

## 页面优化

- 画像摘要与明细分开，摘要按修订复用，明细有界加载。
- 轨迹总览按显示粒度聚合，所选消息优先作为所在桶的代表；执行表格使用有界消息分页，完整记录可按稳定身份读取。本次不新增表格虚拟化或轨迹局部范围接口。
- 轮次导航保持完整，正文载荷增加有界读取，长记录按需展开。
- 地图轻量结果与诊断分开，减少同版快照重复解码。
- 候选数据库索引先验证执行计划、查询耗时、额外存储与写入成本。

## 空间回收

- 用户要求已释放空间不长期占用磁盘。
- 采用 INCREMENTAL 配合后台有界批次，最终回收到接近零；任务忙碌时短暂延后。
- FULL 作为已评估的替代方案保留在研究记录中；后台有界批次便于控制写入竞争和单次工作量。
- 自动回收不等同于重排页内内容，也不能消除全部页内空隙；WAL 另按 checkpoint 和文件回收策略处理。
- 当前主库为 NONE，切换需在数据库初始化或受控转换时建立所需结构；不能仅设置参数就宣称旧库已支持。
- 采用 INCREMENTAL 后台有界回收，扩展既有仅启动维护约定；NONE 旧库仅在受控启动维护、空间和逻辑一致性检查通过时转换，失败不发布不完整数据。
- 官方机制：[auto_vacuum 与 incremental_vacuum](https://sqlite.org/pragma.html#pragma_auto_vacuum)、[VACUUM](https://sqlite.org/lang_vacuum.html)。

## 后续验收设计

- 无变化检查不重新解析或重写正文；来源继续追加、改写、截断和依赖变化按支持能力处理。
- 不同增量阶段与完整重处理的消息、搜索、配对、用量、分支和复制记录统计一致。
- 并发任务不重复、不漏记录，失败和中断不发布半成品。
- 新版应用保留选中会话、定位、筛选和阅读位置；多标签页、隐藏恢复、语言及主题切换均覆盖。
- 消息、画像与轨迹载荷有界，完整正文和证据仍可读取。
- 自动回收后逻辑内容、消息键、FTS 与版本引用一致；长时间重复更新不累积无界空闲空间。
- 性能指标先固定匿名规模、稳定来源与运行条件，再确认预算；单次真实样本不作为固定倍数承诺。

## 实施边界

- 后台分批回收、自动应用新版、检查全部 Agent；多标签页由服务端合并触发。
- 保留完整解析作为正确性基准；来源改写、截断、未知依赖及非追加格式回退，不能仅靠 Agent 最近时间跳过来源。
- 优先减少未变来源读取和缓存重写，有界查询采用可选契约，不改变旧调用的完整数据语义。
- 跨模块正文共享先评估；没有一致性收益证据时不在本次引入大范围消息存储迁移。
- 直接在 main 开发，按项目约定不创建开发分支；实现和集成验收任务见 map.md。
