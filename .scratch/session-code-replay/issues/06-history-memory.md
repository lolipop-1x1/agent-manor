# 大型真实历史归并内存修复

Status: complete

Blocked by: 04

## 问题与范围

- 真实日常服务重启时会按既有策略自动重分析仓库，大型历史分析 Worker 出现堆内存溢出。回放 GET 没有创建刷新任务。
- `resolveSharedHistory` 首次归并每条事件时深复制整个工具输入、输出与历史片段，叠加已保留的解析来源正文；二次水合归并还会增加峰值。
- 仅修改归并所需的容器复制，正文保持只读共享；不提高堆限制、不改启动刷新策略、不裁剪历史、不修改原始来源。

## 验证

- 冻结来源与嵌套正文，验证输入不变、未知升级、来源合并、冲突及复制身份边界。
- 合成 24 MiB 正文的归并额外堆占用由约 24.10 MiB 降至约 0.04 MiB。该微实验不等于真实进程的总内存用量。
- 类型／构建、相关与全量测试、独立源码审查，再用真实完整仓库重分析观察结果与进程 RSS。
- 真实标识、路径与内存诊断只留本机忽略目录；公开文档保留聚合方法和边界。

## 结果

- 独立审查确认当前消费链只读使用正文，没有发现 P1/P2；相关归并、历史与生命周期 134 项通过，全量 1498 项通过。
- 使用相同默认堆限制与日常完整索引重启后台，当前仓库分析任务约 145.98 秒成功发布；三个登记仓库的最新任务全部完成。观测的服务进程峰值 RSS 为 4632 MiB，包含整个进程各线程，不等于单个 Worker 的 JS heap。
- 新版真实回放返回 363 轨／6471 步／14711 条活动，双版本一致；原始证据成功回读，120 次帧回调均值约 6.94 毫秒、95 分位约 7.1 毫秒，期间没有回放 API 请求。
- 此结果消除了该次样本此前复现的溢出，不能推导任意规模历史的内存上限；全量分析仍需数分钟及较大内存。
- 最终接入只读回放 Worker 后再次成功分析并发布，任务约 116.07 秒，观测的整个服务进程峰值 RSS 为 4925 MiB。该轮复用了更多旧来源与映射，不与上一轮直接作等负载速度比较。
