# 验证记录

## 自动化与隔离页面

- 验证压缩发现、逐帧读取、明文／压缩副本、原始字节指纹、解压行号及证据回读。
- 验证损坏与截断帧不能用成功前缀覆盖已发布版本；无变化刷新复用两个物理来源但只发布一个原生会话。
- 验证原生 Skill 注入在排行、画像、证据与会话定位中的一致性；触发与正文只计一次，复制历史排除，独立会话不按正文合并。
- 验证同线程压缩续段的字节／ordinal 边界、来源歧义、分支尾部排除、物理来源定位与前缀改写；旧缓存必须经标准刷新重建，暖刷新复用不累计。
- 合成复现无原生消息 ID 时，两个分段相同行号导致前段 Skill 记录被覆盖；分段兜底身份修复后保留两条证据，旧分段缓存只重建一次，再次刷新不重计。真实核对的原生证据均有消息 ID，事件身份保持不变。
- 覆盖解压量、原始输入和单条证据大小的边界；恰好达到上限允许，超一字节失败。
- 正式构建通过 Chrome 资源工作区 48 项回归；全部管理写操作只使用隔离人工资源。
- 最终代码全量自动化 1,379 项通过，包含边界专项 18 项；共享工作区合并后的类型和国际化检查通过，正式构建通过。一次 MCP 浮层悬停超时后，未修改产品代码的完整浏览器重跑全部通过。

## 性能

- 最大只读压缩样本约 137 MB，解压约 455 MB，逐次读取约 0.70／0.77 秒，进程峰值 RSS 约 139 MB；头部发现约 1.1 ms。普通目标样本约 13 MB→52 MB，读取约 88 ms，头部约 1.5 ms。这是解压读取成本，不包括 JSON 解析和 SQLite 写入。
- 对同一份 20,206 条合成事件数据读取相同的 2,205 条结果：配对查询从 18.08 秒降至 57–191 ms，结果哈希相同。优化只约束相关调用索引，避免优化器按会话重复扫描覆盖索引；不将这一查询的比例外推为整个应用的提升。
- 首次历史回补与后续无变化刷新分别计时；不能以服务已监听或任务进度达到发布前阶段代替回补完成。
- 首次 Codex 回补检查 2,126 个来源，端到端约 26 分 54 秒；CLI 回补检查 5,431 个来源，包含一次服务重启后按检查点继续，端到端约 28 分 49 秒。发布阶段包含旧版本全文索引清理，不能把该耗时归到解压读取，也不能省略。
- 连续跨客户端回补后，分段补全的最终续跑检查 2,139 个来源，仅重解析 8 个，解析约 28 秒；两版本保留策略使该轮发布承担上一代完整 CLI 版本约 120 万条旧消息的全文索引清理，端到端约 45 分 10 秒。运行采样确认耗时位于 FTS 删除，不能把这段成本误记为重新扫描或解压全部历史；此前被中断的清理轮次不计为成功。
- 最终分段缓存升级检查同一批 2,139 个来源，复用 2,134 个，仅重解析目标分段及期间变化的 5 个来源，端到端约 52 秒。随后无变化 CLI 刷新检查 5,431 个来源，全部复用、重解析为零，约 0.94 秒；正式版本和证据集合不变。旧版本清理后的一次检查曾因后台整理排队约 90 秒，不能混作稳定暖刷新成本。
- 新版本首次资源清单请求约 7.18–10.00 秒，包含盘点与统计缓存建立；最终暖清单约 25–43 ms，三个目标详情约 90–108 ms。冷请求与暖请求分别记录，不宣称首次访问已经消除等待。
- 另对临时合成库的 12 万条消息／两类 FTS 做反序重复对照：关闭删除标记触发的合并，将级联删除 9 万条的耗时从 557–566 ms 降到 419–434 ms，但稀疏保留查询从 0.40–0.46 ms 升到 1.34–1.61 ms，保留更多索引段。命中哈希一致、已删除命中为零，但存在明确读性能代价，本轮未调整全局合并配置，不能外推该小库结果到真实大索引。配置语义参考 [SQLite FTS5 deletemerge](https://www.sqlite.org/fts5.html#the_deletemerge_configuration_option)。

## 历史核对方法

- 原始历史只读，原生注入的独立扫描不调用正式 Skill 提取器；私有事件明细与截图仅保留在本机忽略目录。
- Codex 扫描全部普通与压缩历史；CodeFlicker 定向扫描命令标记候选，并逐调用 ID 排除工具结果伴随展开的重复计数。
- 依据原生会话、消息身份、资源名称与路径逐条对账，核对证据行、时间、排行与会话并集。
- 标准刷新回补后再次检查，确认事件集合不累计；校验收藏、手动来源、操作记录和恢复材料的行数及内容哈希。
- 共享服务中途被其他本地任务重启，未提交的版本清理事务回滚；已解析检查点保留并再次对账，继续经标准刷新发布。不能把中断轮次记为已完成的回补。
- 发布后对账另发现一个同线程分段来源；原生边界核验确认前缀有六条独立展开。修复后只读重放逐条核对原消息身份、路径与物理行号，六条均恢复；随后标准回补与最终构建再次验证其正式证据。
- 最终发布的 Codex 原生展开 196／196、CLI 原生展开 257／257 与独立原始扫描逐条一致，漏项、额外项、重复项和字段不匹配均为零。已配对显式调用的 SDK 正文展开不另计读取。
- 对回补前的完整资源清单比较，125 个已有 Skill 增加使用记录，其中 26 个从零恢复为有使用；未发现计数下降。再次刷新后目标的次数、会话并集和证据 ID 集合不变。
- 最终构建通过真实 Chrome 页面核对两个漏计目标的列表、详情、唯一证据条数和会话来源跳转；内置浏览器复核正式页面。收藏、手动来源、操作记录及恢复材料的内容哈希保持一致；其他客户端的已发布会话未受本轮改动影响。

## 支持边界

只统计已核验的显式调用、成功文件读取与客户端原生展开；普通提及、目录清单、任意示例、未核验别名不补造使用。无明确复制关系的不同原生会话不能仅凭相同正文或 UUID 合并。超长单行及未支持客户端的历史缺口仍按原有规则保留，不宣称覆盖所有实际使用。
