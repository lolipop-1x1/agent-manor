# 单字与双字搜索优化设计确认

Type: grilling
Status: resolved

## 目标

补齐短关键词的索引查询能力，减少计数与分页的重复匹配，并隔离慢查询对其他请求的影响。本文记录设计确认，不表示代码或迁移已实现。

## 已确认边界

- 保留标题和所选消息正文的连续字面匹配，沿用筛选、时间排序、精确总数、会话分组与旧版本语义。
- 在现有 SQLite 中增加短词索引；以带位置的字符索引为首选验证方案，最终结构以同数据的速度、空间和字面结果对照选择。
- 保留三字符及以上的既有 trigram 路径。Jieba 分词、相关性排序和语义搜索不属于此次优化范围。
- 复用一次精简候选来计算总数和当前页，仅对当前页读取摘要及会话信息。
- 搜索执行从服务主线程分离，限制排队、淘汰过期任务；运行中的取消能力必须实证验证。
- 匹配存在性检查找到第一条就结束，减少无关筛选依赖和重复请求。
- 首次建设由 Worker 分批处理并可续建，后续随消息事务维护。完整就绪后启用，刷新失败继续提供上一完整版本。

## 设计树

1. 匹配含义与结果契约：已确认，保持现有行为。
   - 单字、双字、多语言混合与特殊字符必须与原有字面查询一致。
   - 高频词不允许静默截断或返回不完整总数。
2. 候选结构：首选带位置字符索引，实施前需与更紧凑候选做基准对照。
   - 速度验收目标：先建立基线，再确定具体时限。
   - 新增常驻空间预算：速度优先，按实测结果评估，无预设 1 GiB 上限。
   - 具体词项生成及维护方式：由代码和实验事实确定，无需用户选择 API 或 tokenizer。
3. 查询执行隔离：已接受方向，运行中取消、连接初始化与版本一致性为技术验证项。
4. 迁移与维护：沿用现有完整版本边界，具体批次与调度由实测确定。
5. 交付验收：依赖 Q1、Q2 和技术验证结论。

## 当前轮问题

- Q1：常见关键词的重复查询以首屏接口低于 750ms 为目标，高频单字单独验收；还是所有关键词都按同一目标，或先建立基线后定值？推荐常见词 750ms、高频词独立验收。目标不是已验证的性能承诺。
- Q2：新增常驻索引以 1 GiB 为预算，超出就比较更紧凑结构；还是速度优先，按实测结果再定预算？推荐先使用 1 GiB 预算。该数值是待确认约束，不是体积估算。

## Answer

用户确认先建立基线再确定耗时目标，速度优先、空间预算按实测结果决定。结合此前按建议优化的授权，设计确认完成。带位置字符索引是首选验证方案；最终候选结构以同数据基准的速度和空间结果选择，不改变字面结果契约。驱动无公开运行中中断接口，SQL 执行中的取消必须单独验证；维护与完整性检查须覆盖全部连接入口。


实施验证选择单字与相邻双字词项，不保存位置。双字候选与带位置方案一致，空间更小；字符交集会保留分散字符的多余候选。补充按消息类型读取文档键的紧凑索引，短词先求候选交集再读取正文。长词保持原 trigram 候选路径。完整性、旧版本和结果对照由存储回归与隔离实验验证。


高频单字复测表明，逐条读取正文做 LIKE 核验仍有明显开销。单字和相邻双字词项可在索引时完整遵循 ASCII 大小写与 NUL 终止规则，因此短词直接使用精确词项判定；三字符以上仍使用候选加 LIKE。固定种子的 Unicode、符号、NUL 与大小写组合测试直接比较索引文档键和原 LIKE，不通过正文过滤掩盖多余候选。真实返回结果也与扫描逐字段核对。
