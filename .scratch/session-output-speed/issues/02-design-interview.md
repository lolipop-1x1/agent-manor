# 吐字速度与执行轨迹设计访谈

Type: grilling
Status: resolved
Blocked by: 01

## 目标

在已完成的[可行性研究](01-feasibility.md)基础上确定吐字速度的统计口径、展示范围、算法帮助与缺失状态，整理成[首版规格](../spec.md)。本任务推进设计，不实施产品代码。

## 已确认

- 展示覆盖右侧用量，以及对话、全部记录和执行轨迹。
- 轮次标题显示本轮平均值；已关联的模型消息与请求用量记录显示所属请求速度。
- 通过合适位置的帮助图标展示算法与统计范围。
- 用户可见标题统一使用“执行轨迹”。
- 文档直接描述自身设计与算法，不写外部产品参考来源。

## Comments

### 第一轮

Q1：采用输出不少于 200 Token、估算耗时不少于 1 秒的显示门槛。用户选择推荐方案。

Q2：模型调用本身被取消、只保存部分输出时，不计算速度、不进入平均值；详情说明响应未完整结束。已经完成的请求不会因为所属轮次后来中断而被整体排除。用户选择推荐方案。

已将模型请求、吐字速度、历史估算吐字速度、平均吐字速度和执行轨迹的定义写入根术语表。算法帮助入口、首版来源支持范围及后续边界继续按访谈轮次收敛。

### 第二轮

Q3：采用区域帮助图标与请求详情的代入算式。消息卡片只显示紧凑请求速度，区域帮助解释通用公式、门槛、范围与平均值。用户选择推荐方案。

Q4：第一版支持 Codex、Claude Code 和 CodeFlicker CLI；桌面原生镜像放到下一阶段。用户选择推荐方案。

已核对现有 HelpPopover、模式翻译键与数据传递链路。帮助复用统一组件；可见名称修改不改变稳定的 `trace` 模式值。

### 第三轮

核查发现当前用量结构没有统一的逐请求完成状态；最终回答和模型请求结束不是同一概念。Q5：用户选择接受明确结束或可靠的历史边界结束推断，并在依据里注明。明确取消／部分响应继续排除，无法确认结束时显示数据不足。

前三轮的选择已写入规格，整体共同理解在最后一轮核对。产品代码、翻译目录和测试尚未修改。

### 第四轮：整体规格确认

Q6：用户确认完整设计已达到共同理解，选择形成待实现任务。不存在未回答的设计分支；统计、展示、帮助图标和名称以[已确认规格](../spec.md)为准。

## Answer

设计完成。第一版支持 Codex、Claude Code 和 CodeFlicker CLI 的历史估算吐字速度，门槛为 200 Token、1 秒，接受明确或可靠推断结束，排除部分和未知结束。四处视图共享请求数据与同范围平均值，算法采用区域帮助图标和详情代入算式，名称统一为执行轨迹。桌面镜像和独立速度曲线留在第一版范围外。

已更新根术语表，形成实施任务 [03](03-request-timing.md)、[04](04-profile-refresh.md)、[05](05-speed-views.md)、[06](06-validation.md)，均置为 `ready-for-agent`，按依赖顺序启动。产品功能尚未实现；本次完成的是设计与任务准备。
