# 会话库吐字速度可行性研究

> 整理日期：2026-10-09。范围：只读检查历史格式、解析链路和计时证据。本文是可行性结论，不构成实现授权。

## 结论

可以给有逐模型调用用量和时间线索的会话显示**历史估算输出速度**，但当前来源普遍没有同时保存单次 API 调用的开始、首字和结束时刻。全局历史不能普遍还原首字后的实际生成速度；可靠的跨客户端字段是部分来源中的输出 Token、请求身份和消息时间。

首版若采用历史估算响应速度，应明确标记为 `≈ tok/s`：按单次模型调用的输出 Token 除以估算响应耗时。这个区间通常包含请求准备和首字等待，客户端事件还可能有持久化延迟。缺少请求身份、结束时间、可判定的调用边界，或记录代表压缩／复制而非新请求时，应显示无数据。若产品要表达严格的“首字后的生成速度”，必须有 `ttft` 及完整调用耗时的持久化计时。

在本次检查范围内，**没有确认任何已接入的原生会话历史能够直接计算逐请求的首字后速度**。MyFlicker 运行时存在更完整的 LLM 生命周期计时事件，但此前核查没有在会话主历史及已检查的运行时日志中找到可用的持久化记录；接入这些计时记录之后才能作为直接计时来源。参考指标定义和当前解析链：[指标与证据口径](../../../docs/design/metrics-and-evidence.md)、[全局客户端注册](../../../src/history/adapters/index.ts#L16-L27)、[会话用量结构](../../../src/session-contracts.ts#L39-L50)。

## 口径与可行条件

应将两种含义分开：

| 指标 | 计算 | 历史来源的支持情况 |
| --- | --- | --- |
| 历史估算响应速度 | `≈ 输出 Token /（估算的调用结束时刻 − 估算的调用开始边界）` | 多种来源可用逐调用用量、请求身份及相邻事件时间尝试估算；不能保证剔除首字等待、请求前本地停顿或记录写入延迟 |
| 首字后生成速度 | `输出 Token × 1000 /（单次调用总耗时 ms − 首字耗时 ms）` | 当前会话历史普遍缺少持久化 `ttft` 与单次 `duration`；仅有未来接入运行时生命周期计时并持久化后可直接计算 |

分子应使用来源报告的**单次调用输出 Token**，不要将整轮或会话总量分摊到助手消息，也不要按可见字符数替代 Token。不同客户端／服务的 `output_tokens` 与推理 Token 关系并不统一；不要一概把 `reasoning_output_tokens` 加到输出量。该数值应称 Token/s，而不是汉字/秒或屏幕逐字速度。

历史估算至少需要唯一到单次逻辑模型调用的用量身份、可解析的时间戳、与该调用对应的响应端时间、可解释的前序请求边界，以及去重后的输出用量。重试可能复用逻辑调用身份；不得把身份字段直接等同底层 HTTP 尝试。小样本阈值和无效耗时下限属于产品口径，应另行校准，本研究不定具体门槛。

## 客户端计时支持矩阵

这里“可历史估算”表示源码字段足以尝试计算带 `≈` 的单次响应速度，不代表首字后精确速度已实现。“需进一步核验”表示存在可能有用的用量／时间字段，但当前关联或粒度不足以作为估算依据。本表对 Codex、Claude 的字段存在情况有小范围匿名结构抽样支持；CodeFlicker CLI 和桌面采用本对话前序已完成的只读核查，其余客户端仅为当前适配器源码初核，未扫描其真实历史。

| 客户端／来源 | 支持判断 | 已有字段与主要限制 |
| --- | --- | --- |
| Codex JSONL | **可历史估算** | 现代 `token_usage_record` 有 `response_id`、单次 `usage`、累计线程用量及事件时间；旧 `event_msg/token_count` 有 `last_token_usage` 与累计检查点。两种形式都没有记录单次 `duration` 或 `ttft`。现代 `response_id` 在抽样中不等于 `response_item.id`，需按事件顺序归组，不能直接凭 ID 将用量挂到单条正文。详见下节。 |
| Claude Code JSONL | **可历史估算** | 助手记录有 `message.id`、`message.usage.output_tokens` 和各条记录的时间戳。流式／分块记录可能各有不同外层 `uuid`，但同一次调用共享 `message.id`；要先按该请求身份合并累计用量，不能按 UUID 计多个请求。无请求起始、TTFT 或总耗时字段。 |
| CodeFlicker CLI | **可历史估算** | 原生助手历史有 `usage.output_tokens`、消息时间及 `metadata.requestTokenBaseline.requestId`。可按逻辑请求和相邻用户／工具结果边界估算；该时间差包含首字等待，旁路 chunk 计时未启用时也没有流式首字时刻。请求旁路日志不是所有安装默认都记录 chunk。 |
| MyFlicker 桌面 | **缓存不足；原生镜像是估算候选** | 主缓存有 `usage.outputTokens` 和消息时间，但 `duration` 是用户轮次开始至消息物化的累计时间，可能混有其他模型调用和工具等待，不能直接作为单请求分母。通过 `lastEntryUuid` 可关联 `claude-session` 原生记录以取得更合适的请求身份、用量及消息时间；当前适配器只从镜像读取模型和请求 ID，需要扩展映射，并核验镜像中的请求边界后才能使用。已检查的主历史和日志没有提供可用的 `llm.start`／`llm.first_token`／`llm.end` 持久化计时。 |
| CodeFlicker IDE（旧／新 SQLite 主历史） | **当前来源不足** | 主历史适配只提取消息、行级时间和工具过程；现有核查中的回答记录没有逐请求输出 Token 与完整调用耗时。部分旧记录的 TTFB 单独不能得出 Token/s。当前解析器也把其累计缓存明确标为不足以重建请求趋势。 |
| DeepSeek Harness | **需进一步核验** | 原生 `assistant/message`／`assistant/attempt` 可带用量和事件时间；还记录 `turn/start`、`step/start`、`step/end`。适配器当前将步骤事件规范化为上下文记录，尚未证明一个 step 边界等于一次模型 API 调用，也未保存首字时间。 |
| Pi | **可历史估算** | 助手消息有事件身份、时间戳和 `message.usage`；助手调用及工具过程按事件树关联。独立 `usage`、压缩摘要及分支摘要也可能带用量，不能在没有助手请求身份关联时当作普通回复速度。 |
| WorkBuddy | **可历史估算** | `message` 事件有时间和消息身份，适配器从 `providerData.usage`、`message.usage` 等投影归一化用量并识别请求键；若投影互相矛盾会保留歧义。无起始／首字／结束耗时；请求粒度和不同提供商历史仍需逐格式校准。 |
| OpenCode | **需进一步核验** | 助手消息有 `time.created`／`time.completed`，步骤用量位于 `step-finish` part；适配器将步骤用量事件时间取自 `time.start` 或 part 创建时间。消息结束可能跨越多步或工具调用，不能直接充当每个步骤的结束时间。需要按 step 身份核验真实配对及计时语义。 |
| ZCode | **需进一步核验** | `model_usage` 有尝试身份、`assistant_message_id`、输出 Token 与 `started_at`；旧研究记录到该表有耗时相关原生字段，但当前适配器只读取 `started_at` 和用量，未确认可用的结束／首字字段及语义。核验原生列和对应助手消息后，可能比相邻消息差更精确。 |
| CodeBuddy | **当前来源不足** | 当前适配器仅将已确认的用户消息作为正文事件，其他记录类型／角色及 provider 用量留采集缺口；本地既有样本也仅覆盖用户消息。 |
| Qoder | **可历史估算** | 助手记录有时间、原生消息／记录身份及可归一化的 `message.usage`。无请求开始、首字或单次耗时，重试粒度与不同历史版本的身份语义仍待样本确认。 |

CodeFlicker、DeepSeek Harness、Pi、WorkBuddy、OpenCode、ZCode、CodeBuddy 与 Qoder 的适配器入口集中见 [客户端注册](../../../src/history/adapters/index.ts#L16-L27)。以上分类描述当前可见的适配器字段，不声称全部历史版本都具有相同记录覆盖。

## Codex：现代记录与旧 token_count

会话解析器会读取现代 `token_usage_record.payload.usage`，以 `response_id` 作为请求身份，并把 `thread_token_usage` 用作累计进度；旧 `event_msg` 的 `token_count` 使用 `last_token_usage` 与 `total_token_usage`。原生格式小范围匿名抽样中，现代记录有事件时间和输出用量字段，但未见 `duration`、`ttft`、显式开始／结束时间字段。抽样只验证当下默认来源的字段形状，不代表所有历史版本。

现代记录的 `response_id` 不是助手响应项的 `id`。当前解析器没有猜测正文关联，而是单独保留用量事件。因此实现任何速度估算都需要按同一来源内的事件顺序关联一组助手响应项和其用量记录，不能仅依靠请求 ID 连接。

旧格式 `token_count` 没有独立请求 ID，必须结合 `total_token_usage` 检查点去重；不能按相同 `output_tokens` 值合并请求。当前代码已在两种记录顺序下去重新旧投影，并保留不同 `response_id` 的独立请求；现有合成测试对此有覆盖。来源身份和累计检查点处理见 [parser-usage.ts](../../../src/sessions/parser-usage.ts#L10-L78)、[Codex 记录分支](../../../src/sessions/parser.ts#L327-L350) 与[合成测试](../../../tests/session-parser.test.ts#L277-L288)。

旧格式计时至少有这些边界：

- **工具等待**：一次模型调用可先输出工具请求，再等待工具结果后继续调用。不能把工具执行耗时或整轮耗时放进前一次模型响应分母；使用 `token_count` 作为结束点前，需确认它没有在旧日志中延迟到工具结果之后才写入。若延迟，须依据同一响应的最后助手输出时间校正，并经样本验证。
- **并行工具**：工具结果可能乱序返回。下一次模型调用的有效边界只能在其所需的工具结果齐备并进入下一次请求后确认，不能随便取一条并行结果的时间。
- **中断和末尾不完整记录**：中断可以没有完整助手输出或用量；JSONL 半条末记录会留为缺口。不能补出零时长或完整响应速度；若保留部分速率，应另标部分响应。
- **复制历史和分叉**：解析器按明确继承边界将 `copied` 记录排除，计时和汇总也必须排除，不要把共享前缀再计一次。
- **压缩与用量重置**：压缩后的零值 `token_count` 可能是累计状态重置，不必然是零 Token 的模型调用。仓库有待处理的压缩重置识别问题；速度统计必须先区分重置与真实零输出请求，参见[既有问题记录](../../session-history/issues/09-compression-usage-reset.md)。
- **重复呈现**：同一次用量可能同时出现在现代记录和 `token_count` 投影中。必须先依响应身份／累计检查点去重再汇总；相同用量值也可能属于不同请求。

工具与中断的现有记录规则见 [parser.ts](../../../src/sessions/parser.ts#L195-L228)、[Codex 工具结果处理](../../../src/sessions/parser.ts#L347-L415) 和[中断／复制测试](../../../tests/session-parser.test.ts#L394-L416)。当前测试验证对话和用量去重，不是速度边界验收。

## Claude：分块消息身份

Claude 原生流式记录使用外层 `uuid` 标识各条历史记录，而 `message.id` 标识对应助手模型消息。当前解析器据外层 UUID 稳定区分消息内容，再按 `message.id` 合并同一次模型调用的用量投影；多次保存的累计 `output_tokens` 由后写入的快照更新。匿名原生结构抽样观察到同一 `message.id` 横跨多条具有不同 UUID 和时间戳的助手记录；没有输出正文、身份值、时间值或来源路径。这个小范围抽样证明当前样本存在分块形态，不证明所有版本或会话必然如此。

因此速度需以 `message.id` 为一次逻辑请求的分组单位，先取最后一个有效累计输出用量，再按请求组取时间。不能按每个外层 UUID 各造一次请求，也不能把累计快照重复相加。现有解析器把合并后的 `occurredAt` 更新为最后的时间戳，没有保留首个片段时间；所以从历史估算完整响应速度可尝试从前序有效边界计至末条记录，若要用首末分块时间近似首字后速率，则必须先验证时间戳精度、流片段写入语义及末片是否完整。实现依据见 [Claude 请求身份与用量解析](../../../src/sessions/parser.ts#L417-L485)、[用量合并](../../../src/sessions/parser-usage.ts#L22-L46) 和[分块合成测试](../../../tests/session-parser.test.ts#L290-L305)。

## 验证方法与限制

- 对本仓库进行源码只读核对，读取根 [CONTEXT.md](../../../CONTEXT.md)、[领域文档规则](../../../docs/agents/domain.md)、相关 [ADR 0005](../../../docs/adr/0005-rebuildable-global-session-index.md)、[ADR 0006](../../../docs/adr/0006-scoped-session-refresh-verification.md) 和[指标与证据口径](../../../docs/design/metrics-and-evidence.md)。
- 仅对 Codex 与 Claude 默认历史做匿名结构字段抽样，用来确认请求身份、用量和时间戳是否共存及分块身份关系；检查输出仅包含字段有无／关系结论。抽样采用最近更新文件，非随机、非全量，不作覆盖率或跨版本保证。未将真实正文、身份值、完整时间、来源路径、公司内部域名或业务信息输出或写入本文。
- CLI 与桌面字段结论引用本对话前序已完成的本机只读核查；本轮没有重复扫描对应原始历史。其余客户端未检查实机数据。
- 读取现有合成解析测试以确认身份、去重和复制边界；本轮未改代码，也未运行测试。源码字段核验不等于浏览器、刷新或真实历史速度验收。

## 设计进展

后续设计采用历史估算吐字速度，明确包含首字等待与可能的请求准备。用户已确认显示门槛为输出不少于 200 Token、估算耗时不少于 1 秒，部分响应不计算速度；通过区域帮助图标解释算法，请求详情显示代入算式。第一版支持 Codex、Claude Code 和 CodeFlicker CLI，桌面镜像下一阶段。完整设计与待确认边界见[规格草案](../spec.md)。

## 会话库接入评估

### 推荐首版范围

采用**历史估算响应速度**，先支持 Codex、Claude Code 与 CodeFlicker CLI。每次逻辑模型调用显示 `≈ 24 tok/s`；时间边界不明确、缺少输出用量或样本过短时显示 `—`。MyFlicker 桌面先核验原生镜像边界，其他客户端在各自时间与请求身份语义校准后逐个启用，不能仅凭两个时间字段就默认支持。

这不是一次用户提问、整个会话或单个消息片段的速度。同一次调用的多个内容块与累计用量快照先合并，再产生一个速度。工具调用参数属于模型输出；工具执行等待要尽量从相应请求区间中排除。首版不通过可见文本长度估算输出 Token，不使用会话墙钟时间分摊请求耗时。

### 现有数据链路可以复用

建议的数据流为：`原生历史事件 → 按请求归组并计算计时依据 → SessionUsage → session_usage JSON → SessionProfile.steps → 用量表、轮次标题、消息卡片与执行轨迹`。

| 接入位置 | 当前能力 | 实现时需要补充 |
| --- | --- | --- |
| [SessionUsage](../../../src/session-contracts.ts#L39-L50) | 单次用量身份、输出 Token、事件时间与消息定位 | 可选的请求计时资料：有效耗时、计时口径、估算方法以及起止事件依据；不要复用工具消息的 `durationMs` |
| [请求用量归组](../../../src/sessions/parser-usage.ts#L10-L78) 与 [来源解析](../../../src/sessions/parser.ts) | 多快照合并、请求去重、消息及轮次关联 | 在读取原始事件时识别每次请求的起止边界；归组完成后结算，不在界面上用相邻行时间相减 |
| [用量 JSON 存储](../../../src/sessions/store.ts#L189-L217) | 完整保存用量对象，同请求身份更新快照 | 可保存新增可选字段，不需要为首版另建请求表或清空数据库 |
| [Profile 汇总](../../../src/sessions/store.ts#L754-L845) | 按当前索引版本读取全部请求，排除已确认复制记录，支持包含子会话 | 对有合格计时的同口径请求子集汇总，同时返回可计算数量与总请求数量 |
| [刷新与缓存](../../../src/sessions/refresh.ts#L86-L139) | 来源与元数据指纹、客户端范围刷新、原子发布新版本 | 给受影响客户端增加计时解析规则指纹，使正常刷新重新解析其历史；无须触发无关客户端重建 |
| [桌面原生镜像映射](../../../src/sessions/codeflicker-desktop.ts#L48-L76) | 通过 UUID 关联镜像，当前保留模型和请求身份 | 若支持桌面，扩展为请求组与起止事件资料，并保留旁路来源指纹与读取限制 |

已有用量对象没有计时字段时继续表示缺失，正常刷新后可对原始历史仍可读且边界合格的请求回填。Profile 查询从索引读取计时，不在打开页面时扫描原始历史。当前 Web 与 CLI 共用 Profile 契约，计时元数据也可同时进入 CLI JSON。

### 界面与汇总

展示范围包括右侧「用量」页，以及主内容区的「对话」「全部记录」「执行轨迹」。各处复用同一份请求速度与计算依据，近似数值直接带 `≈`，通过明确标签区分单请求速度和轮级平均速度。以下数值均为合成展示示例。

| 视图与位置 | 显示示例 | 数值范围 |
| --- | --- | --- |
| 对话：轮次标题旁 | `第 14 轮 · 平均 ≈ 32 tok/s`；部分可计算时附 `3/4 次可计算` | 该视图当前分支、本会话该轮内的合格模型请求；用请求输出总和除以同一批请求耗时总和 |
| 对话：AI 回复卡片标题旁 | `模型名称 · 请求 ≈ 40 tok/s` | 有明确关联的单次模型请求；一条回复跨多个请求时不挑选一个值冒充整条回复速度 |
| 全部记录：AI、思考或请求用量卡片标题旁 | `思考 · 请求 ≈ 40 tok/s` | 该记录所属的单次模型请求；不是该思考片段或正文片段的独立生成速度 |
| 全部记录：轮次标题旁 | `第 14 轮 · 平均 ≈ 32 tok/s` | 与当前视图的轮次及分支范围一致；不能混入别的轮次、分支或子会话 |
| 执行轨迹：在「输出／结果」之后、「时间／耗时」之前增加「速度」列 | 模型／请求用量行显示 `≈ 40 tok/s`，工具执行、工具结果、用户等行显示 `—` | 已确认关联的单次模型请求；工具运行时长继续属于工具耗时 |
| 执行轨迹：选中记录详情标题旁 | `#42 · 思考 · 请求 ≈ 40 tok/s` | 与所选记录所属请求一致，详情展开输出 Token、估算响应耗时与起止记录依据 |
| 右侧用量：请求明细表与平均值 | 每行 `≈ 40 tok/s`；平均值附可计算请求范围 | 明细按单次请求，平均值按「当前会话／包含子会话」选定范围 |

对话与全部记录共用[轮次容器](../../../web/Sessions.tsx#L65-L81)及[消息卡片](../../../web/SessionMessage.tsx#L63-L82)，适合统一复用紧凑速度标记。轮次折叠时仍显示平均值；消息卡片按明确请求关联展示。卡片尚未确认请求关联时不补猜测值；已关联但计时缺失时可显示 `请求速度 —`，详情解释原因。不存在模型请求的轮次不显示速度；存在请求却全部无法计算时，轮次显示 `速度数据不足`。

同一个请求可以包含多个思考、文本和工具参数片段。模型片段若共享请求，显示同一个请求速度，并在帮助或详情说明；汇总始终按唯一请求身份去重。仅有 Token 总用量而没有片段用量时，不拆分出“思考速度”与“回复速度”。

当前[执行轨迹关联](../../../web/session-trace-model.ts#L32-L46)主要使用 `usage.messageId`。Codex 的用量目前[定位到独立用量记录](../../../src/sessions/parser.ts#L153-L158)，并没有对应到每条思考／回复。要在这些模型卡片和表格行显示速度，需要解析层保存可解释的请求与模型消息组关联，不能在界面用“同一轮”或“最近一条用量”替代关联。无法确认关联时，可继续在明确的请求用量行与合格的轮级汇总中显示。

执行轨迹扩展现有[表格](../../../web/SessionTrace.tsx#L100-L132)与[详情](../../../web/SessionTrace.tsx#L136-L150)，保留虚拟滚动与固定行高，速度标记不产生多行常驻说明。各视图从同一索引版本的数据构建按请求、消息和轮次的映射，避免逐卡片反复扫描全部请求。

右侧「用量」页现有[请求明细表](../../../web/SessionProfile.tsx#L169-L177)增加可选速度列。存在速度记录时显示该列，缺失请求显示 `—`；全会话无合格记录时显示 `速度数据不足`。沿用现有请求定位、分页、主题、共享中英文目录以及 `HelpPopover`，每个区域复用或合并帮助入口。统计公式与边界按需展开，估算和部分可计算状态直接可见。

当前趋势图的纵轴是 Token 数量，不应将 Token/s 作为同轴曲线加入。首版可以在选中请求的提示中补速度，独立速度趋势图留作后续需求。

如果展示会话平均速度，计算应为：

`同口径合格请求的输出 Token 总和 / 同一批请求的有效耗时总和`。

不能简单平均每行 Token/s，也不能将全部输出 Token 除以只有部分请求具备的耗时。汇总要显示可计算请求范围，例如合成示例 `18/30 次可计算`。估算与直接计时、含首字等待与首字后等不同口径分开；缺失不能当作零。包含子会话时仍按请求耗时求和，并行请求的时间会重叠，所以该平均值不表示整项任务相对于墙钟时间的处理速度。

### 风险、验收与工作量判断

接入数据契约、JSON 存储与用量表的结构难度较低，主要工作在**逐来源校准请求计时边界**。整体是中等范围功能；无法仅靠增加一列表格完成。精确首字后速度需要采集并持久化运行时事件，属于另一项工作。

实现时应使用合成历史测试覆盖：单请求、一次调用多个助手片段、不同请求用量相同、现代／旧用量重复投影、工具等待、并行工具结果、中断、复制前缀、压缩重置、无效／逆序时间、缺失计时和短响应过滤。存储测试应验证全部请求的明细与合格子集汇总一致，包含子会话后不重复统计，并验证旧索引刷新回填与作用范围。

界面验收应覆盖中英文、深浅主题、窄屏、分页、缺失与部分可计算状态以及请求原文定位；还需验证对话／全部记录的轮次折叠、同请求多个模型片段共享数值但不重复汇总、分支与子会话范围、执行轨迹新增列及虚拟滚动、选中详情与右侧用量的一致性。仅用合成样本运行管理写操作；真实历史只在本机做脱敏数值与边界校准。本轮仅完成源码与字段可行性核查，未实现或运行上述验收。
