# CodeFlicker 接入与客户端扩展规格草稿

日期：2026-10-05。已确认 C1、C2、C3；C4 历史范围和最终共享理解尚待确认。本文件不表示功能已经实现。

## 目标

将 CodeFlicker 作为独立 Agent 客户端接入代码活动地图，同时建立可继续增加内置客户端的接入边界。
沿用当前仓库基线、原始证据、精确／近似对应及结果版本口径。

## 已确认范围

- 分析 Agent 会话的文件读取、修改、搜索和活动次数；读取与修改分别统计。
- 支持 Web、CLI、API 与已有 Agent 查询 Skill；可单独筛选 CodeFlicker，也可查看全部客户端。
- 提供文件与行覆盖、当前代码范围、历史事件和原始记录回查。
- 只读本机已有历史；缺少结果、成功依据、内容或范围时保留采集缺口。
- 本轮不增加采集 Hook，不纳入代码补全和编辑预测，不增加可单独安装的第三方插件。

## 可扩展接入边界

1. 客户端声明集中维护稳定 ID、显示名称与来源配置，API 校验、CLI 帮助和 Web 筛选共用这些信息，移除“所有非 Codex 都是 Claude”的判断。
2. 客户端身份与历史格式分别表示；一个客户端可以采用不同格式，多个客户端也可以共享同一格式适配器。来源和事件始终保留实际客户端身份。
3. 内置格式适配器负责来源元数据、记录解析、请求与结果配对、续读状态、父子／分叉关系及原始证据回查。当前 JSONL 的物理行与哈希定位仍然保留。
4. 适配器将客户端原始记录转换为通用事件、证据片段、来源引用与采集缺口；能复用的工具证据规则继续复用，新工具规则按实际执行记录核对。
5. 仓库归属、内容对应、覆盖统计、完整版本发布与查询继续消费通用模型，无需了解 CodeFlicker 的原始记录结构。
6. 来源配置以纯数据传给 Worker，适配器实现由 Worker 加载。仅增加客户端身份不要求 SQLite 表结构迁移；实际引用和缓存变更仍需核对兼容与重建规则。

扩展验收目标：接入符合现有证据模型的新客户端时，新增声明、来源／格式适配和测试即可贯通各查询入口，不再逐处增加客户端判断。若未来来源需要新的证据定位形式，在适配边界扩展，不将原始格式判断散落到页面与统计层。

## 待确认历史范围 C4

推荐首版分析 `~/.codeflicker/projects` 中的主会话及能够确认归属的子会话，并支持显式来源目录配置。
`requests/` 不作为独立活动计数来源；SQLite、MyFlicker 和未核对的归档形式暂作为后续格式候选，不宣称已支持。
最终范围以 C4 回复为准。

## 已核对样本与实施门槛

- 主会话存在 `config/message` 记录，包含 `sessionId`、消息身份和 `promptId`；样本未见 `cwd`。
- `tool_use.id` 与 `tool-result.toolCallId` 可配对，结果有 `llmContent` 等内容字段；可按原始物理行和记录哈希回查。
- 有结果不直接表示成功。必须核对失败字段、缺失字段的语义及工具返回结构后，才确定成功判定规则。
- 修改覆盖必须来自实际执行的工具参数、结果与修改内容；模型请求内的示例或重放内容不作为已执行修改。
- 仓库归属必须有来源元数据、实际绝对路径或可核实的项目关系支持；不只凭目录 slug 猜测工作目录。
- 子会话、分叉和重复来源只有在身份关系有证据时去重；相同内容或调用 ID 不单独证明重复执行。
- 原始会话和请求文件只读，不执行历史命令、不上传历史、不调用模型判断覆盖。

上述成功语义、编辑证据、仓库归属和精确子会话关系仍待核对。实施先完成代表样本与支持矩阵，不以未知字段推高覆盖。

## 验收

- 格式样本覆盖成功、失败、缺失结果、截断、尾记录、重复消息、重复调用 ID、子会话及真实重复活动。
- 读取与修改有能够回到原始执行记录的真实样本；精确、近似、未知保持现有口径。
- 选择由实际 CodeFlicker 证据可归属的真实 Git 仓库，完成登记、刷新、Web 地图、CLI／API 查询和证据回读。
- Web／CLI／API 显示同一客户端身份和同一结果版本，CodeFlicker 筛选不混入 Claude 事件。
- 重复刷新不增加同一活动，追加与缺失来源遵循现有规则；requests 中的重放不重复计数。
- 已有 Codex／Claude 的统计、筛选、配置与证据回查通过回归。
- 核对实际安装包中的内置声明、适配器、Worker 和 Web 资源；记录真实来源规模及刷新表现，不以目录清点代替运行验收。

## 尚未完成

本轮仅完成需求讨论、代表样本调查与架构边界核查，没有实现、运行适配器或完成 CodeFlicker 端到端验收。
