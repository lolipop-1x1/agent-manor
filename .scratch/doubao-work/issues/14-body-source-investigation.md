# 核查客户端可见回复与本机正文来源的差异

Type: research
Status: resolved
Blocked by: 13

## 目标

用户提供的客户端截图显示完整回复，但同一会话在 AgentManor 只有摘要、没有正文。继续核查来源覆盖，不能把本机摘要的空 messages 解释为原生会话没有回复。继续遵守本机来源限定，不调用云端历史、不读取登录凭证、不抓取进程内存、不生成替代历史。

## 验证范围

- 重读实时启动页和聊天页缓存，按原生会话身份匹配所有投影，再对比日常服务 messages API。
- 检查消息加载及持久化调用链，区分摘要、会话页内存状态、任务恢复状态与完整历史归档。
- 补查嵌套 WebStorage、原生 shell LevelDB、内部扩展和非认证 HTTP 缓存响应体；负向标记扫描不用于证明所有本机位置均不存在正文。
- 真实标识、路径、原文、脚本及详细结果仅保存于忽略目录；公开记录只保留方法和边界。

## Answer

调查完成，正文缺口未修复。实时重读同一会话的四份列表快照，messages 均为零；日常服务消息 API 同样为零。客户端截图与接收完成日志证明回复存在，不能据此将来源空值等同于原生没有消息。

已定位的历史加载链为 `initMessageList` → `/im/chain/single` → 扩展 HTTP bridge → 远端 HTTPS `fetch()` → message_list 规范化 → 前端消息内存 store。部分会话列表请求显式不取消息，普通最近列表也有默认带近期片段的分支；不能概括为所有 recent_conv 都不取消息。任务检查点和协议 task map 用于未完成任务恢复，完成路径清理；检查时相关状态为空，不能作为已完成历史库。

补查嵌套 IndexedDB、原生 shell LevelDB、内部扩展会话类键、非认证 HTTP 响应体、目标工作区轨迹和应用日志后，仍未取得目标回复的完整本机正文。LevelDB 检查包含活跃 manifest、WAL、表和按块 Snappy 解压；HTTP 正文包含常见压缩与编码以及 JSON/SSE 标记核对。嵌套查询缓存为市场元数据，原生任务轨迹只有用户片段。已核验安装版本的关键历史模块一致。

这些定点结果不能证明所有本机组件或版本均不存在私有消息副本；少量 HTTP 响应布局也未识别。当前仅本机来源边界下，尚无已核验的新来源可用于实现正文补齐，不调用云端、不用截图或推断填造历史。来源文档已明确区分调查完成与正文兼容完成。公开内容和 diff 格式检查通过；本轮无运行代码变化，没有将复现仍为零的场景描述为通过验收。

## Comments

- 后续按用户指定的“有正文／无正文”两条会话实时对照：有正文会话在启动页 conversations 聚合快照中有 6 条原生消息，经过程块规范化为 44 条记录；同会话在聊天页的聚合占位和四份列表摘要均为零。无正文会话仅在四份列表摘要出现，原生 messages 均为零，工作区轨迹只含两条 user 记录。直接运行适配器和日常服务 brief/full API 结果一致；同步状态 complete、stale=false，排除旧索引或阅读模式导致差异。
- 原生会话元数据关联的客户端版本分别为 2.25.17 和 2.32.12；两者会话类型及模式相同。这是跨版本写入行为变化的线索，不单独视为升级导致缺失的因果证据。后续核查结果见下一条。
- 当前安装包定点核查补全：普通 recent 列表请求 `limit:20`、`message_count_per_conv:10`、`not_need_message` 默认 false，非项目调用明确 true；loader 可裁剪非当前／非特定会话的正文，新式列表状态持久化面向摘要。请求差异由列表选项决定，未发现依据会话模式或元数据版本决定正文缓存的分支。旧 `conversations` store 直接写入点仍未定位，不能把某项机制当作缺失会话的已确认具体触发。
- 上述结果修正了早先“recent_conv 请求显式不取消息”的过宽概括：仅部分调用如此。来源文档同步修正；没有修改运行代码或将正文缺口标记为修复。额外目标回复标记在本次 826 条非认证 HTTP 缓存响应体中未命中，负向检查边界不变。
- 最后一轮限定扫描覆盖当前 Browser Framework 的全部 local_webcontents 文本资源，未定位账号分区 conversations 的直接写入者；该缺口保留，不再凭现有静态资源推断单一原因。
