# 较多速度分组使后续查询返回 HTTP 431

Type: task
Status: resolved
Priority: P2

## 触发条件

速度报告含较多客户端、模型和计时口径组合。服务端默认选中全部分组；前端随后将完整分组键数组写入地址和 GET 查询。

## 复现

建立 120 个合成模型，每个模型一条有效 Codex 请求，全部属于同一本地日期。

首次 `includeSpeed=true` 请求没有显式分组，返回 HTTP 200，报告含 120 个分组并全部选中。将报告中的 `selectedGroups` 原样作为 `speedGroups`，再将时间粒度改为周；查询字符串为 17,850 字节，实际服务返回 HTTP 431：请求头超过允许大小。

这些分组数量未超过接口的 500 项限制。触发阈值还取决于模型名、计时字段和其他筛选的实际长度，120 不是固定边界。

## 预期

合法默认选择应支持后续时间粒度、分页和刷新操作。应控制选择的传输体积，不能只依赖数组项数校验。

## 位置

- `src/usage/speed.ts:60`：未指定时默认选中全部分组。
- `web/features/usage/Usage.tsx:114-119`：将默认分组同步为显式数组。
- `web/features/usage/model.ts:54-57`：数组序列化进 GET 查询参数。

## 验证边界

通过真实 HTTP 服务和合成持久化索引确认；未修改服务器限制，未核查真实历史的分组数量。

## 修复

默认全选保持隐式。Web 与 CLI 的长筛选通过 POST 请求体读取，报告、状态和请求明细复用 GET 校验与响应结构。真实 HTTP 回归覆盖 500 个长模型分组；CLI 同时验证传输与摘要／完整响应兼容。
